# invoke architecture audit

Date: 2026-09-02. Tree: `test/pin-attribution-and-pool` at 92a1483 (eight commits past v1.1.0). Status: baseline green (go vet, all three golangci-lint configurations, race tests on both modules); 107 findings confirmed, 4 refuted, 20 folded at dedup. While the audit ran, that branch merged as #70 and a separate session landed #71 (main at 49278de), which closes F99 and F100; the entries below say so and plan items 4 and 6 are marked landed. Every other line number refers to 92a1483.

## Verdict

The library is in good health at the level a user sees. The root package is small and coherent, the error taxonomy is stated once and honoured, the four providers share one lifecycle shape (Start ordering, Once-guarded Wait, close-then-kill-then-Wait) and one vocabulary of error prefixes and sentinels, and the contract suite is an executable specification with a self-test that proves every contract can fail. The prose is careful sentence by sentence. Nothing here needs a rewrite. Most of what follows is moving, renaming and correcting rather than redesign; the few day-or-more items are the transfer path and the fake's shell.

The debt concentrates in three places. First, the transfer path: the engine exists three times (internal/transfer, docker's tar path, the fake's hand-rolled path), the two off-engine copies have already drifted on the download side (symlink policy ignored, progress paths wrong), the contract suite proves every transfer policy through Upload only so the drift was invisible, and the concurrency change in #69 left one real correctness gap (a cancelled pooled tree copy can return nil with files missing). Close never reaches an in-flight transfer on any provider and each provider fails that case differently. Second, provider consistency below the contract level: the environment registry with its race-closing re-check is pasted into four packages and the fake's copy lost the re-check; the POSIX pre-flight script is written twice in two dialects that disagree about shell builtins; an eight-line random-name helper exists three times with two policies; attribution names drift between the four process types. Third, the ssh package carried one authentication defect nobody filed (a key file that is rejected shadows the agent for good, because both are the RFC method "publickey" and x/crypto tries one method per name) and an undocumented password-first precedence; both were fixed in #71 while this audit ran, and the residual is the agent socket's reliance on ambient environment (F101).

What is in good shape: the contract suite's design and its self-proof; the jump-host chain and the pool, which reused existing vocabulary rather than inventing parallel mechanisms; the per-file atomic delivery and containment logic in the engine as it stood before #66/#69; the docker context resolution; the local terminal lifecycle; the build tooling, which pins its linter through one file and runs the same commands in CI and locally. The repository-level documents are the exception to the prose quality: README, CONTRIBUTING, SECURITY and the release tooling still state a pre-1.0 versioning policy two releases after v1.0.0, RELEASING.md's guard has already been skipped once, and no document tells a contributor how the tree is laid out, which is the gap that let files land under different names in different packages.

## Map

Read in this order: doc.go, interfaces.go, errors.go, executor.go; then internal/transfer/transfer.go from Copy downward; then one provider's environment file, process file and transfer file; then invoketest/invoketest.go and a provider's test that calls Verify. Nothing in the tree says this today (F78).

**fake/ (9 files).** fake.go: a good package doc that is the one place the shell subset and builtin vocabulary are enumerated, plus Environment, Start, LookPath, Close, name resolution, Handler/Session/Option; process.go: the simulated lifecycle with a stated abandonment protocol; shell.go: a refusal scanner, then the executor, splitter, tokenizer and expander; builtins.go; vfs.go the node store; fsview.go an io/fs adapter; transfer.go a hand-rolled Upload/Download. The lifecycle is the strongest part. transfer.go predates the engine extraction by hours and was never moved onto it, and has drifted (F52). shell.go scans the grammar three times with the quote state machine written out in each, which is the surface #20/#28/#29 kept appearing on (F53); the refusal at Start compares the raw path so `/usr/bin/sh` bypasses it (F54); `exec` is implemented and undocumented (F55).

## Findings

Severity reflects reader and caller impact after the verifiers' refinements; effort is S (under an hour), M (a session), L (a day or more).

### 1. Transfer path

**F72. Concurrent tree copy reports success after the caller cancels.** Severity high. Effort S. Files: internal/transfer/pool.go, internal/transfer/transfer.go, internal/transfer/transfer_test.go, invoketest/contracts_transfer.go.
Problem: pool.fail discards every context error including the caller's own, and copyTree returns pool.wait() then walkErr without consulting ctx.Err(). Once the walk has returned nil and the caller cancels, every in-flight copy fails with Canceled, fail drops it, wait returns nil, the chmod pass runs and Copy returns nil with files missing. Reproduced by three verifiers (two 200 KB files, WithConcurrency(2), cancel with both parked on their first write: nil, zero entries delivered). Both cancel contracts transfer a single file, which bypasses the pool, and ssh's default hint of 8 puts every real tree upload on this path.
Evidence: pool.go:91-104 (fail), transfer.go:267-315 (copyTree; the pool section at 288-303), transfer.go:140-144 (single-file route), contracts_transfer.go:190-223 and 457-486 (single-file cancel contracts).
Proposal: after pool.wait(), return the caller's ctx.Err() (the caller's ctx, not pool.ctx, which the pool cancels on any failure) when it is done; precedence: recorded pool failure, walk error, caller's ctx, then chmod. Add a unit test on rendezvousFS asserting ErrorIs Canceled and no delivered entries, and an invoketest contract `cancel-preserves-tree-destination` with WithConcurrency > 1 asserting ErrorIs Canceled and no `.invoke-` temp files or torn content (not an empty destination, since a real provider may finish a file before observing the cancel), with its misbehave defect. Say on Environment.Upload that cancellation surfaces as ctx.Err().

**F93. Close never reaches an in-flight transfer; four providers, four outcomes.** Severity high. Effort L (ssh half S). Files: interfaces.go, ssh/files.go, ssh/environment.go, docker/files.go, docker/environment.go, local/files.go, fake/transfer.go, executor.go.
Problem: interfaces.go promises that after Close every method fails wrapping ErrClosed, but every Close snapshots only processes and every transfer path calls checkOpen once at entry then watches only the caller's ctx. On ssh, Close ends in chain.Close, pkg/sftp broadcasts a connection-lost error to in-flight requests, isTransportFailure matches it, and the caller's own Close comes back as a retryable TransportError, which Executor.retryTransfer then backs off on and retries into a closed environment. On docker, client.Close only drops idle connections; CopyToContainer completes and moveRemote and removeRemote issue new execs through runRaw after Close returned, so Upload returns nil. On local and fake the copy finishes and returns nil. The process side reads closedByUser before classifying (ssh/process.go:442-444); the transfer side does not.
Evidence: interfaces.go:13-14; ssh/environment.go:166-168, 185; ssh/files.go:69, 128-130, 246-273; docker/environment.go:172; docker/files.go:57, 67; docker/process.go:533-549 (no checkOpen); local/files.go:15, 30; fake/transfer.go:23, 62; executor.go:219-240.
Proposal: in two steps. (1) ssh, regardless of the rest: in transfer(), after a failed run read e.closed under e.mu before classifyTransfer and return an error wrapping ErrClosed, mirroring attribute's closedByUser-first order; executor.terminal already refuses to retry anything wrapping ErrClosed (executor.go:363). (2) Give each Environment a lifetime context created in New and cancelled by Close (simpler than a registry of closers), derive every transfer's working context from it and the caller's, and check `errors.Is(context.Cause(ctx), ErrClosed)` before classifying; docker then cancels CopyToContainer and never issues moveRemote after Close while removeRemote keeps its detached cleanup context but bails when closed; local and fake derive for uniformity. Keep the keepalive-detected dead link as TransportError; the distinction is exactly e.closed. Write the decision into interfaces.go's Lifecycle sentence and pin it with the contract in F94.

**F52. The fake re-implements the transfer engine and has drifted from it.** Severity high. Effort L. Files: fake/transfer.go, fake/vfs.go, fake/fsview.go, internal/transfer/transfer.go, transfer.go, invoketest/contracts_transfer.go.
Problem: the engine's package doc says a provider plugs an FS into Copy rather than re-implementing the semantics per transport; local and ssh do so in ~40 lines each; fake/transfer.go carries nine hand-rolled functions (uploadTree ... downloadFile, hostContains), re-derives ClassifyEntry's message and EffectiveMode, and copies HostFS.Contains. The engine was extracted (0876339) three hours after the fake landed (993f31d) and the fake was never migrated. Verified drift by running it: Download with SymlinkSkip still creates the link, download progress reports `path.Base(vpath)` where TransferProgress.Path is documented as root-relative, and cfg.Concurrency is never read. The fake's selling point (README, fake.go:1-10) is that it cannot drift from real providers; for transfers it does. Upload does enforce host containment (hostContains at :169); the gaps are on the Download side.
Evidence: fake/transfer.go:91-406, :132-148, :216-219, :264-267, :373, :380-383, :404-406; internal/transfer/transfer.go:1-7; contracts_transfer.go:270, 573, 633 (Upload-only policy checks).

Upload becomes `transfer.Copy(ctx, transfer.HostFS{}, local, vfsFS{e.fs}, remote, cfg)` and Download the mirror, as local/files.go reads; delete the nine functions; copyChunkBytes returns to being cat's private buffer. Land after the download-side contracts in F96 so the drift is pinned for every provider, not only the fake.

**F41. docker's tar.go/untar.go mirror engine helpers with the rationale only in git history; Download ignores the symlink policy.** Severity high. Effort M. Files: docker/tar.go, docker/untar.go, docker/files.go, internal/transfer/transfer.go, internal/transfer/hostfs.go, transfer.go.

Evidence: docker/tar.go:244-280 vs internal/transfer/transfer.go:671-703 and hostfs.go:38-40; docker/untar.go:176-196 vs transfer.go:425-446; untar.go:317-339 vs transfer.go:511-527; untar.go:89-90, :226-232; transfer.go:153-155 (EntryAction doc).

Treat SymlinkFollow on Download separately: the archive carries only the link target, so following needs a container-side resolution step with containment or an explicit ErrNotSupported by name; decide and document which.

Add a target-side `test -L` probe to symlinks-preserve so the true half of SymlinkPreserve is verified on the target rather than inferred from the round trip.

## Cleanup plan

One decision gates several items and should be taken first.

**D1: may the docker module import the core module's internal/ packages?** Go's internal rule is path-based, so `github.com/ruffel/invoke/docker` may import `github.com/ruffel/invoke/internal/...` and an overlay build confirms it compiles. Commit 9a51d35 removed such an import because a published module would depend on an unversioned package. The counter-argument: docker pins the core by exact version, the two are released together under one number, and internal packages are covered by that pin as much as any exported one; the versioning hazard is only that a core minor may change an internal API, which the paired release already handles. Recommendation: allow it for mechanism (lifecycle registry, randomSuffix, posixsh, testcontainer), keep policy (ClassifyEntry and friends) exported because third-party providers need it regardless (F03's intent lens), and write the rule into CONTRIBUTING's layout section.

Two constraints shape the order. First, docker's tests run under go.work and see the local core, but `just check` tidies docker with GOWORK=off against the pinned tag, so a docker import of a core package that the pinned tag lacks turns the tree red. A new core package therefore lands, gets tagged, and only then does docker import it; the plan puts the core halves of the shared mechanism before the release checkpoint and the docker halves after. Second, new invoketest contracts need no tag: the docker lane runs them under the workspace as soon as they exist. If D1 is "no", items 26 to 29 still land for the in-module providers, item 30 is dropped, and docker keeps its copies.

## How this audit was run

Fifteen area readers each summarised one slice of the tree (root, local, ssh source, ssh tests, docker source, docker tests, fake, invoketest, internal/transfer, provider consistency, public API docs, repository docs and build, test architecture, recent changes, and a metrics pass over function length, nesting, file size and duplication) and filed candidate findings with file and line evidence. Candidates were deduplicated (twenty bundles were split or merged into their canonical finding) and each survivor was put through three adversarial lenses independently: accuracy (does the evidence check out on disk, reproduced where feasible), documented intent (does a commit, comment or document justify the current shape), and value (would a thoughtful maintainer act on it). A finding needed two of three lenses to confirm; verifiers' refinements were folded into the proposals above and severities adjusted where a lens argued them down. A final review re-opened every cited file and line against 92a1483 and re-sequenced the plan around the docker module's pin. #70 and #71 merged to main while the workflow ran; the audit was reconciled against them afterwards (F99, F100, plan items 4, 6, 9 and 21). Result: 111 findings verified, 107 confirmed (11 of them with one refuting vote and a narrowed proposal), 4 refuted. Nothing a linter enforces was reported; the tree passes all three golangci-lint configurations, go vet and the race tests on both modules at 92a1483.
